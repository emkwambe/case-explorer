# Dataset Card: Case Explorer governed splits

## Dataset summary

Eight fully synthetic tabular datasets of US mortgage applications, generated by the Case Explorer simulator and written by `scripts/build_datasets.js`. Each row is one application as an underwriter would see it: claimed values, evidence values, claim-versus-evidence discrepancies, underwriting ratios and application metadata. Alongside each row, and never merged into it, sit synthetic sensitive attributes for fairness testing and the generator's own labels.

The eight splits are one baseline population split three ways plus five purpose-built regimes: a later origination date under a rate shock, a high-cost geography skew, a subprime-heavy population under a larger rate shock, adversarial fraud placement, and a corruption-free negative control.

Build them with:

```bash
npm run datasets
# or: node scripts/build_datasets.js --out analytics/data --train 6000 --seed 42 --as-of 2026-01-15
```

The CSVs and their manifests are gitignored; the counts below come from a run at generator commit `93bf79b`, dataset version 2.1.0, recorded in `analytics/data/datasets.manifest.json`.

## Supported tasks

| Task | How the data supports it |
|---|---|
| Fraud detection | `label__is_fraud` and `label__fraud_type` over nine injected typologies, with a clean negative control for false-positive measurement |
| Underwriting decision modelling | `label__expected_outcome` (`APPROVE`, `MANUAL_REVIEW`, `DECLINE`) and `label__reason_codes` from the governed catalog |
| Fairness testing | `sensitive__*` columns, held out of every decision input, supporting subgroup slicing and counterfactual twins |
| Drift monitoring | Four stress splits generated from the same schema under shifted populations and rate environments, each with its own configuration hash |

## Languages and locale

English, US mortgage conventions: annual salary in USD, monthly obligations, back-end DTI, PITI, five-digit ZIP codes, W-2 wages, credit-bureau tradelines and scores, 30-year fixed-rate product. There is no free text; every field is numeric or a categorical code.

## Data structure

Rows are flat CSV. Columns fall into three families, governed by `src/decisioning/policies/feature_policy.js` (policy version 1.0.0) and documented field by field in `docs/methodology/DATA_DICTIONARY.md`.

| Family | Prefix | Policy class | Contents |
|---|---|---|---|
| Permitted features | none | `PERMITTED` | Loan terms, claims, evidence values, claim-versus-evidence discrepancies, underwriting ratios and application metadata. 55 columns. These are the only columns a rule or a model may read. |
| Sensitive attributes | `sensitive__` | `SENSITIVE` | `age`, `age_band`, `region`, `geography_group`, `income_band`, `family_status_scenario`, `disability_income_scenario`, `persona`. Never a decision input; available to fairness testing only. |
| Labels | `label__` | `PROHIBITED` | `case_id`, `is_fraud`, `fraud_type`, `severity`, `expected_outcome`, `reason_codes` (pipe-joined), `regime`, `split_hint`. Blocked from training and scoring. |

Discrepancy columns are claim-versus-evidence only. Anything computed against world truth is prohibited leakage and is rejected at runtime by `enforceFeaturePolicy` in strict mode, which is also what the `permissible_variables` release gate checks. `label__is_fraud` is 1 for the nine fraud typologies and 0 for both `NONE` and `INCOHERENT`, since the incoherent split is a negative control for impossible worlds rather than for deception.

The feature policy itself is exported to `analytics/data/feature_policy.json` and the ruleset to `analytics/data/fraud_rules.json`, so the Python layer enforces the same rules as the JavaScript layer.

## Data collection

There is no collection. Every record is generated, and no real person, employer, lender, account or credit file is involved at any point.

The generation process, per case:

1. A financial life is sampled: demographics, persona, employment and income trajectory, liabilities, assets, credit score, housing and rent history, geography and population regime. Correlations between age, salary, DTI, checking balance and credit score come from a five-variable Gaussian copula configured in `src/distribution_config.json`.
2. A closed-loop monthly cash-flow ledger is simulated backwards from the sampled balance, enforcing `ending_balance = starting_balance + salary_deposits - total_outflows`.
3. A claimed application is deep-copied from that truth, then a corruption operator may mutate the claim, the evidence or the world itself.
4. Evidence documents are synthesised from the ledger (W-2, employer verification, bank statement, credit bureau, rent verification, geographic verification) with per-document fidelity noise, then typology-specific evidence effects are applied.
5. Application metadata is drawn from either a clean or a signalled regime.
6. `extractDecisionFeatures` projects the case down to the underwriter-visible row written to CSV.

Everything is seeded. A given seed and configuration reproduce the identical corpus, which is what the `reproducibility` release gate verifies.

Each split writes `analytics/data/<split>.manifest.json` carrying the dataset version, generator version, case schema version, feature schema version, ruleset version, generator commit, a SHA-256 configuration hash, the seed, the as-of date, record and fraud counts by typology, outcome counts and a SHA-256 of the CSV file. The index at `analytics/data/datasets.manifest.json` collects them. Metrics are only comparable across runs that share the dataset version, configuration hash and generator commit.

## Annotation

There are no human annotations and no observed outcomes.

`label__expected_outcome`, `label__reason_codes`, `label__is_fraud` and the alignment level are produced by the generator's own decision engine (`computeDecision` in `src/core/findings.js`), which reads the corruption type and world truth directly. `label__fraud_type` and `label__severity` are simply the injection parameters recorded back.

These are policy-derived labels, not outcomes. No case has a repayment history, delinquency, default or loss. A model trained here learns to recover a documented injection mechanism, not to predict a real event. Section 6 of `docs/methodology/LIMITATIONS.md` sets out the circularity this creates between the labels and the rule baseline that was written against the same operators.

## Personal and sensitive information

No personal information of any kind is present. Names, SSN last-four values, ZIP codes, employer names, IP addresses and document metadata are sampled from configured distributions and correspond to nobody. Device fingerprints and IP addresses are unique per case.

The `sensitive__` columns are synthetic scenario labels. `family_status_scenario` and `disability_income_scenario` are sampled independently of every financial variable and carry no real-world meaning. `age_band`, `income_band`, `geography_group` and `persona` are deterministic functions of the generated financial life and are therefore correlated with outcomes by design. No race, ethnicity, sex, national origin or religion is modelled, and no proxy structure for them exists in the data.

All of these attributes are isolated from decision inputs by the feature policy: they are exported in their own column family, they never enter a rule or a model, and the `permissible_variables` release gate fails the build if any prohibited or leaking column reaches a decision input.

## Social impact and bias discussion

The fairness controls attached to these datasets, and what they mean:

- **Subgroup analysis** compares selection ratios and outcome rates across the `sensitive__` groups with two-proportion tests. On the independently sampled scenario attributes the observed minimum selection ratio is 1.000 with no significant disparities. On the derived attributes (income band, age band, persona) ratios fall well below four-fifths, which is expected: those attributes are functions of the same financial variables the policy underwrites on.
- **Counterfactual invariance** flips each sensitive attribute on a case and rescores. The decision layer reports 4,311 pairs across 300 cases with zero changed outcomes, and the model layer 22,800 pairs across 300 rows with zero changed scores.

What this does **not** establish: nothing about disparate impact on real applicants. The attributes are synthetic, the population is synthetic, no protected class is modelled, and the artifacts carry their own disclaimer that these are technical fairness-testing controls that support rather than replace human legal and compliance review. They do not establish compliance under ECOA, the Fair Housing Act, Regulation B or any other regime.

The main misuse risk is treating measured performance on these splits as evidence about a real lending population. It is not, and any figure quoted from these datasets should be quoted with the manifest that produced it.

## Known limitations

The full statement is `docs/methodology/LIMITATIONS.md`. The points that most affect use of these datasets:

- No parameter is fitted to real data; none reaches the `EMPIRICALLY_CALIBRATED` provenance class in `docs/methodology/PARAMETER_SOURCES.md`.
- One product only: 30-year fixed mortgage, loan amount fixed at three times stated salary, one rate, one tax and insurance proxy.
- No property, appraisal, LTV or down payment applied to the loan.
- One applicant per case; no co-borrowers or household structure.
- Application metadata is separable by construction, so metadata features will dominate any model trained here and any measured lift from device or behavioural signals is an artefact of the injection design.
- Labels are policy-derived and circular with the rule baseline.
- No observed outcomes, so bad rate and expected loss are proxies that cannot be validated.
- Evidence documents are structured JSON fields, not images or PDFs, so nothing here supports document forensics or OCR work.
