# Credit PD model: data

_Generated by `python -m case_analytics.credit.docs --write` from `artifacts/credit-model-snapshot/`. Do not edit by hand; `--check` fails if it is out of date._

## How the data was produced

`node scripts/export_credit_features.mjs` reruns the Solar prime book pipeline (`buildSolarBook`, the same code that builds the locked seed-42 book) once per seed and writes `data/credit-model/`. The rule: **test** is seed 42, the locked book; **training** is seeds from 1001 upward until the training books' funded loans hold at least 2,000 defaults (1001, 1002, 1003, 1004, 1005, 1006, 1007, 1008); **calibration** is the next two seeds (1009, 1010). Each book funds 10,000 credit-policy approvals in seed order. Every application is simulated by the dealer engine, so all of them carry a 30+ DPD outcome; the headline model uses funded rows only, as a lender would.

The seed-42 files, the teaching and opening-library features, the feature spec and the manifest are committed. The training and calibration books are regenerated (about 3 minutes) and gitignored; `data/credit-model/manifest.json` holds every file's SHA-256, and the Python loader refuses data that does not match it.

**Fairness files** (Sprint 12), seed 42 only and committed: `sensitive-seed-42.csv`, the audit attributes of every application, read only by the fairness group tables and the proxy check and never a model input; `decisions-seed-42.csv`, the credit policy's decision on the claimed FICO (the app's policy, equal to the locked tape) and on the bureau FICO (the bureau-score policy, an evaluation variant only); and `fairness-flips.json`, the counterfactual flip table. Every book also gets its decisions file, gitignored with the book.

## Preparation

- **Features** (from the application, the documents and the loan; `data/credit-model/feature-spec.json`, built by `scripts/lib/credit-features.mjs`):

| Feature | Group | Monotonic | Why |
|---|---|---|---|
| `fico_bureau` | CREDIT_SCORE | −1 (risk can only fall) | A higher credit score never means higher risk. |
| `dti_stated` | DEBT_BURDEN | +1 (risk can only rise) | More debt burden never means lower risk (the simulated hazard is flat below 36%, which the constraint allows). |
| `stated_monthly_debts` | DEBT_BURDEN | +1 (risk can only rise) | More stated debt never means lower risk. |
| `income_stated` | INCOME_LEVEL | −1 (risk can only fall) | More income never means higher risk at the same obligations. |
| `income_overstatement_pct` | INCOME_DISCREPANCY | +1 (risk can only rise) | Stating more income than the employer verifies is misrepresentation. |
| `undisclosed_debt` | UNDISCLOSED_DEBT | +1 (risk can only rise) | Bureau debt the application leaves out is concealment. |
| `undisclosed_accounts` | UNDISCLOSED_DEBT | +1 (risk can only rise) | Bureau accounts the application leaves out are concealment. |
| `checking_overstatement_pct` | ASSET_DISCREPANCY | +1 (risk can only rise) | Stating more cash than the statement shows is fabrication. |
| `statement_excess_pct` | ASSET_DISCREPANCY | +1 (risk can only rise) | A statement showing more cash than stated points to an altered document. |
| `checking_stated` | LIQUIDITY | −1 (risk can only fall) | More stated reserves never mean higher risk. |
| `checking_statement` | LIQUIDITY | −1 (risk can only fall) | More verified reserves never mean higher risk. |
| `overdraft_count` | LIQUIDITY | +1 (risk can only rise) | More overdrafts never mean lower risk. |
| `large_deposits_total` | UNSOURCED_DEPOSITS | +1 (risk can only rise) | Unseasoned deposits inflate apparent reserves. |
| `tenure_months` | EMPLOYMENT | −1 (risk can only fall) | Longer employment never means higher risk. |

- **Discrepancies are one-sided:** the positive part of stated minus verified (or the reverse), so each constraint means one thing. Both checking directions are kept: a fabricated claim states more than the statement; an altered statement shows more than the claim.
- **Excluded:** age, region, zip_code, cost_of_living_index, persona, regime and every audit attribute (sensitive or geographic); the credit bureau's persona field (a generator type, not a lender field); dealer_id (dealer risk belongs to the Dealer View); device and session metadata (fraud signals, not creditworthiness); fraud-rule outputs (reasons come from the raw fields); W-2 wages (a partial-year artefact for short tenures); world truth, the corruption label, dealer quality and PD (answer key only).
- **No cleaning or imputation in the data.** Missing document values stay missing; XGBoost routes them natively, and the logistic baseline imputes the training median.
- **The split is by seed, never by row:** no seed-42 application appears in training or calibration (a test checks it).

**Selection bias, stated plainly.** Outcomes a lender observes exist only for funded loans, so the headline model learns from approved applicants only. The all-applications diagnostic shows what the simulation would let it learn otherwise; the augmented sets below test standard reject inference.

## Augmented training sets (reject inference)

Built in memory by `python -m case_analytics.credit.pipeline` from the training books only (seeds 1001, 1002, 1003, 1004, 1005, 1006, 1007, 1008); no seed-42 row is used, and a check refuses a set that contains one. Before augmentation the training books hold 150,170 applications: 80,000 funded with 2,004 defaults, and 70,170 not funded, whose outcomes a lender would not see (6,167 defaults in the simulation).

## Shifted books (drift)

Built by `node scripts/export_credit_features.mjs` with the same book pipeline as every other book, each from a new seed with one stated change to an existing generator setting (no generator code changes), and an unchanged control seed. Gitignored with the other books; their SHA-256 values are in the manifest under `drift_books`, kept apart from the training, calibration and test seeds. Each book funds 10,000 credit-policy approvals in seed order, so a riskier population needs more applications.
